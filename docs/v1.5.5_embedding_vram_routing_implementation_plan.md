# AgentHub Local v1.5.5 专项实施方案：三级自适应 Embedding 与显存感知 ONNX 硬件加速路由

## 1. 任务背景与工程目标

本方案针对 AgentHub Local 在桌面端运行 Embedding 时的**“实时交互低延迟 (< 10ms)”**与**“大批量建索引高吞吐”**双重诉求，以及**“与本地运行的 Ollama/llama.cpp 大模型显存零抢占防爆”**核心矛盾，实施“三级自适应路由 + 显存感知 ONNX 双会话生命周期”架构升级。

### 四大工程铁律
1. **零抢占本地大模型显存**：在消费级显卡（RTX 4060 8GB / 4070 12GB）上，严禁盲目挂载全局 CUDA Session。单条查询强制走低延迟 CPU 会话；批处理仅在空闲显存 $\ge 2.5\text{ GB}$ 且前台无生成时启动临时 GPU 会话，且显存申请上限硬锁定在 **768 MB**，用完即焚（15 秒空闲自动释放）。
2. **零重型依赖与安装包轻量**：严禁引入 PyTorch / TensorFlow；基础安装包不内置模型文件（增量 $< 35\text{ MB}$），按需静默下载至 `~/.agenthub/models/bge-small-zh-v1.5-int8/` 并强制 SHA-256 校验。
3. **毫秒级查询延迟**：单条 Query 编码 P95 $< 12\text{ ms}$，内存占用 $< 100\text{ MB}$。
4. **异常零抛出与无缝兜底**：任何 GPU / ONNX 异常自动捕获并在同一次调用内由常驻 CPU 会话无缝兜底，终极离线退化为 SQLite FTS5 trigram 纯词法检索。

## 2. 详细技术方案设计

### 2.1 硬件探针显存接口扩展 (`backend/app/probe/collector.py`)
- 在 `CrossPlatformHardwareProbe` 中封装轻量方法 `get_vram_status() -> dict[str, Any]`：
  - 返回：`{"has_gpu": bool, "vendor": str, "total_vram_mb": float, "used_vram_mb": float, "free_vram_mb": float}`；
  - 内置 3.0 秒结果缓存，避免批处理中频繁触发系统调用。

### 2.2 核心抽象与运行态契约 (`backend/app/search/embedding_provider.py`)
- 数据类 `EmbeddingRuntimeStatus`：
  - `tier: Literal["tier1_local_server", "tier2_onnx", "tier3_lexical_fallback"]`
  - `model_id: str`
  - `dimension: int`
  - `active_device: str`
  - `device_policy: Literal["auto", "cpu", "gpu", "directml"]`
  - `is_available: bool`
  - `model_downloading: bool`
  - `download_progress: float`
  - `last_batch_latency_ms: float`
- 抽象基类 `BaseEmbeddingProvider`：
  - `encode_query(text: str) -> np.ndarray | None`（单条查询编码，返回 512 维 L2 归一化一维向量，P95 < 10ms）
  - `encode_batch(texts: list[str], batch_size: int = 32) -> np.ndarray | None`（批量建索引编码，返回 `[N, D]` 归一化二维矩阵）
  - `embed_texts(texts: list[str]) -> np.ndarray`（向下兼容现有接口）
  - `get_status() -> EmbeddingRuntimeStatus`

### 2.3 Tier 1：本地推理引擎复用 (`LocalServerEmbeddingProvider`)
- 探测已注册的 Ollama（`/api/tags`，匹配 `bge`、`nomic`、`m3e`、`embed` 等）或 llama-server（`/v1/embeddings`）；
- 4 字符探针校验连通性；
- 复用已有推理服务，额外内存/显存严格为 **0 MB**。

### 2.4 Tier 2：显存感知轻量 ONNX 引擎 (`VramAwareOnnxProvider`)
- **双会话生命周期设计（Dual-Session Lifecycle）**：
  - **常驻 CPU 会话 (`_cpu_session`)**：
    - 绑定 `CPUExecutionProvider`；
    - 配置 `intra_op_num_threads = min(4, os.cpu_count() // 2)`，`inter_op_num_threads = 1`；
    - 负责单条/小批量（$\le 32$ 条）实时查询编码，规避 CUDA 上下文初始化开销与显存抢占。
  - **按需临时 GPU 会话 (`_gpu_session`)**：
    - 策略门控：`auto` 模式下仅当 `len(texts) >= 64` 且 `free_vram_mb >= 2560` 时拉起；
    - 防爆参数：`CUDAExecutionProvider` 传递 `{"arena_extend_strategy": "kSameAsRequested", "gpu_mem_limit": 768 * 1024 * 1024}`，硬锁定显存上限在 768MB；
    - 闲置回收：记录 `_gpu_last_used_at`，15 秒无新任务或显式调用 `release_ephemeral_gpu_session()` 时销毁并 `gc.collect()`；
    - 故障自愈：任何 GPU 异常立即捕获，自动回退到 `_cpu_session` 完成计算并记录日志。
- **纯 Python Tokenizer 与双镜像源静默下载**：
  - 支持从 ModelScope 或 HF-Mirror 断点下载 `model_quantized.onnx`（约 24.5MB）与 `vocab.txt` / `tokenizer.json`，强制 SHA-256 校验。

### 2.5 Tier 3：极限离线纯词法降级 (`NullEmbeddingProvider`)
- `is_available = False`，上层自动切换为权重 `w_fts=1.0, w_vec=0.0` 的纯 FTS5 检索。

### 2.6 上层协同与多渠道接口适配
- 更新 `HybridSearchEngine`，在 `search` 时调用 `encode_query`，在 `upsert_chunks` 时调用 `encode_batch`；
- API 与全局单例导出。

## 3. 测试与验证策略
在 `backend/tests/test_embedding_vram_routing.py` 中覆盖：
1. 单条实时检索延迟（CPU 模式 P95 < 12ms）；
2. 批量建索引吞吐与向量维度校验；
3. Mock 显存不足（1200MB）严格锁定 CPU 会话验证；
4. Mock 显存充足（5200MB）触发临时 GPU 会话与 15s 闲置回收验证；
5. GPU 异常抛出时的自动平滑回退常驻 CPU 会话。
